# Context Switching — Picasso Design Law §5.5

This document defines Picasso's product-mode detection, composition rules per mode, mode-switching logic, and anti-slop enforcement by mode. Every screen generated by Picasso must first pass mode detection, then conform to the composition rules of the detected mode. Generating content in the wrong mode is a non-negotiable failure.

---

## 1. Product Mode Taxonomy

Picasso recognizes exactly **four product modes**. Every screen falls into exactly one of these modes. A screen cannot be "between" modes — if it is, mode detection has failed.

| Mode     | Alias                  | Core Purpose                                   | User State                      |
|----------|------------------------|-------------------------------------------------|---------------------------------|
| `APP`    | app, dashboard, tool   | Functional workflows. User is *doing work*.      | Logged in, active, task-focused |
| `LANDING`| landing, marketing     | Conversion. User is *evaluating the product*.    | Unauthenticated, browsing       |
| `DOCS`   | docs, documentation    | Information retrieval. User is *learning/reading*.| Either, research-focused        |
| `SOCIAL` | social, feed, community| Engagement. User is *interacting with people*.   | Logged in, social-browsing      |

### 1.1 Mode Is Detected From the Prompt, Not Guessed

Picasso must detect the mode from the user's brief. If the brief is ambiguous, Picasso must ask for clarification rather than guess. Guessing the mode and generating in the wrong one is the single most damaging error Picasso can make.

## 2. Mode Detection Rules

### 2.1 APP Mode Triggers

Detect `APP` when the prompt contains any of:

- **Direct indicators:** "dashboard", "app", "primary screen", "workspace", "tool", "admin panel", "settings", "project management", "CRM", "analytics"
- **Functional language:** "view projects", "manage tasks", "track progress", "edit profile", "configure", "create new", "team dashboard"
- **Data density indicators:** "table", "chart", "kpi", "metrics", "list", "data", "report"
- **Workflow context:** The user describes what a logged-in user does, not what a visitor sees
- **User context:** "team", "workspace", "my projects", "their account" — implies authenticated state

**Example prompts that trigger APP mode:**
- "Design a project management dashboard with a sidebar, project list, and KPI cards"
- "Create a settings screen for notification preferences"
- "Build a team workspace where users can see tasks assigned to them"
- "Design the primary screen for a CRM showing leads, deals, and pipeline"

**APP mode anti-signals (should trigger APP, not LANDING):**
- If the prompt says "app" or "dashboard" anywhere, it's APP mode, even if the screen also has a welcome message or some marketing-style content. The presence of a functional component (sidebar, data table, settings form) overrides any landing-like elements.

### 2.2 LANDING Mode Triggers

Detect `LANDING` when the prompt contains any of:

- **Direct indicators:** "landing page", "hero section", "homepage", "marketing site", "conversion", "pricing page", "about page", "feature page", "product page", "website"
- **Conversion language:** "sign up", "get started", "CTA", "call to action", "convert visitors", "lead generation", "trial", "demo"
- **Narrative structure:** "hero, features, testimonials", "above the fold", "social proof", "customer logos"
- **Visitor context:** "visitors", "prospective customers", "audience", "traffic"
- **Storytelling indicators:** "tell a story", "brand story", "value proposition", "unique selling point"

**Example prompts that trigger LANDING mode:**
- "Design a landing page hero section for a project management SaaS"
- "Create a pricing page with 3 tiers for a design tool"
- "Build a marketing homepage featuring our product's key benefits"
- "Design a feature showcase page with testimonials at the bottom"

**LANDING mode anti-signals (should trigger LANDING, not APP):**
- If the prompt mentions "hero", "visitors", "pricing", "testimonials", or "conversion", it's LANDING mode. Landing pages are about persuasion, not functionality.

### 2.3 DOCS Mode Triggers

Detect `DOCS` when the prompt contains any of:

- **Direct indicators:** "documentation", "docs", "API reference", "knowledge base", "help center", "guide", "tutorial", "developer docs", "wiki"
- **Content structure:** "sidebar with sections", "search bar", "code examples", "endpoints", "parameters", "methods", "quick start"
- **Information-seeking language:** "how to", "reference", "learn about", "find information", "browse topics"
- **Code-related content:** "code snippets", "request/response", "examples", "SDK", "CLI"

**Example prompts that trigger DOCS mode:**
- "Design the API reference documentation page with a sticky sidebar"
- "Create a knowledge base layout with search and category navigation"
- "Build a getting-started guide with code examples and step-by-step instructions"
- "Design a help center with search and collapsible FAQ sections"

**DOCS mode anti-signals:**
- DOCS mode requires a search bar as a prominent UI element. If the prompt has no search and no sidebar navigation tree for sections/pages, reconsider whether it's DOCS or just a content page in APP mode.

### 2.4 SOCIAL Mode Triggers

Detect `SOCIAL` when the prompt contains any of:

- **Direct indicators:** "feed", "timeline", "social", "messaging", "chat", "community", "forum", "activity feed", "notifications", "connections", "profile page"
- **Interaction language:** "posts", "comments", "likes", "shares", "messages", "followers", "friends", "threads", "reactions"
- **Real-time indicators:** "live", "online", "typing indicator", "presence", "notifications"
- **User-generated content:** "user posts", "content feed", "updates from", "what's new"

**Example prompts that trigger SOCIAL mode:**
- "Design a social feed with posts, comments, and a compose button"
- "Create a messaging interface with a conversation list and chat window"
- "Build a community forum with categories and recent discussions"
- "Design an activity feed showing recent team updates and comments"

**SOCIAL mode anti-signals:**
- SOCIAL mode implies a feed or messaging layout. If the prompt is about "viewing content" but there's no feed structure, interaction counts, or compose action, check whether it's actually a content page (APP mode) or a feed (SOCIAL).

## 3. Mode Detection Decision Tree

```
Does the prompt mention a hero section, pricing, testimonials,
OR describe a visitor (not logged-in user) experience?
├── YES → LANDING mode.
│   └── CAVEAT: If prompt also says "dashboard" or "app",
│       the page may be a hybrid. Ask: "Is this the marketing
│       homepage or the authenticated app screen?"
│       If both, generate TWO screens — one landing, one app.
│
└── NO: Does the prompt mention API reference, documentation,
       search-heavy content, code snippets, or "how to" guides?
    ├── YES → DOCS mode.
    │
    └── NO: Does the prompt describe a feed, timeline, messaging,
           posts, comments, or user-generated content stream?
        ├── YES → SOCIAL mode.
        │
        └── NO → APP mode (default).

IF AMBIGUOUS: Ask. Never guess.
```

### 3.1 Ambiguity Resolution Examples

| Ambiguous Prompt                                                                 | Resolution                                                                 |
|----------------------------------------------------------------------------------|----------------------------------------------------------------------------|
| "Design a home screen for a project management tool"                             | Ask: "Is this the marketing landing page or the authenticated app dashboard?" |
| "Create a page where users can see their projects"                               | APP mode — "their projects" implies authenticated state.                   |
| "Design the first screen users see when they open the product"                   | APP mode — "when they open the product" implies after login.               |
| "Design a page about our product's features"                                     | LANDING mode — "about our product" is marketing.                           |
| "Build a screen showing recent activity"                                         | AMBIGUOUS. Ask: "Is this a social activity feed or an app audit log?"      |

## 4. Composition Rules by Mode

### 4.1 APP Mode Composition Rules

**Mandatory elements:**
- Navigation: sidebar (recommended) or topbar. NEVER tabbar on desktop. NEVER footer.
- Content area: functional, data-populated, fills >50% of viewport height with meaningful content.
- No hero section. No centered welcome message as primary content (exception: first-use empty state with no data yet).
- No marketing CTAs ("Get started", "Sign up free", "Learn more").
- No testimonials, no social proof, no pricing, no "features" section.

**Allowed but restricted:**
- Empty states: only for first use or when data genuinely does not exist. Must follow empty state patterns in component-patterns.md §9.
- Welcome messages: small, contextual — e.g., "Good morning, Alex" in the topbar, not a centered hero heading.
- Onboarding overlays: permitted as tooltips or guided tours, not as full-screen marketing sections.

**Layout template for APP mode:**

```
┌──────────────────────────────────────────────────────────┐
│ TOPBAR (h-14/16): Workspace name, Search, User avatar    │
├──────────┬───────────────────────────────────────────────┤
│ SIDEBAR  │ MAIN CONTENT                                  │
│ (w-60/64)│                                               │
│          │ ┌─ Page header: Title + Primary action ─────┐ │
│ Nav item │ │                                            │ │
│ Nav item │ ├─ Content section 1 (KPI cards, chart) ────┤ │
│ Nav item │ │                                            │ │
│ Nav item │ ├─ Content section 2 (Data table / list) ───┤ │
│          │ │                                            │ │
│ Workspace│ ├─ Content section 3 (Activity / details) ───┤ │
│ switcher │ │                                            │ │
│          │ └────────────────────────────────────────────┘ │
│          │                                               │
└──────────┴───────────────────────────────────────────────┘
(NO FOOTER)
```

**App mode forbidden patterns checklist:**
- [ ] Centered hero heading + subheading + CTA? **REJECT.**
- [ ] Footer with links or copyright? **REJECT.**
- [ ] Bottom tabbar? **REJECT.**
- [ ] "Sign in" / "Get started" in topbar? **REJECT.**
- [ ] Sparse content with >50% whitespace? **REJECT.**
- [ ] Testimonials or pricing on the screen? **REJECT.**

### 4.2 LANDING Mode Composition Rules

**Mandatory elements:**
- Hero section: primary visual area at the top. Heading (32–56 px, weight 700), subheading (16–20 px, neutral-600), visible CTA button(s).
- CTA flow: a clear path to conversion. At least 2 CTA placements (hero + bottom).
- Social proof section: customer logos, testimonials, or stats ("10,000+ teams").
- Footer: links, legal, copyright, social media links.

**Optional but typical:**
- Feature section: 3–4 highlighted features with icons/illustrations.
- Pricing section: 3–4 tiers with feature comparisons.
- Testimonials section: customer quotes — in rows, NOT circular-avatar carousels.
- FAQ section: collapsible questions at the bottom.
- Demo/screenshot section: product screenshots or video placeholder.

**Layout template for LANDING mode:**

```
┌──────────────────────────────────────────────────────────┐
│ HEADER NAV: Logo (left) ─── Nav links ─── CTA (right)   │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  HERO SECTION (full-bleed accent wash, py-28/36)        │
│  ┌──────────────────────────────────────────────────┐   │
│  │ Grid 7+5: Text (left) + Image/Illustration (right)│   │
│  │  h1, p, CTA buttons                               │   │
│  └──────────────────────────────────────────────────┘   │
│                                                          │
├──────────────────────────────────────────────────────────┤
│  FEATURES SECTION (py-24)                                │
│  ┌──────────────────────────────────────────────────┐   │
│  │ Section heading + 3-or-4-col feature grid        │   │
│  └──────────────────────────────────────────────────┘   │
│                                                          │
├──────────────────────────────────────────────────────────┤
│  SOCIAL PROOF (full-bleed bg-muted/50, py-24)           │
│  ┌──────────────────────────────────────────────────┐   │
│  │ Logo cloud or testimonial grid                   │   │
│  └──────────────────────────────────────────────────┘   │
│                                                          │
├──────────────────────────────────────────────────────────┤
│  CTA SECTION (py-24, centered, narrow)                   │
│  ┌──────────────────────────────────────────────────┐   │
│  │ h2, p, Primary button (lg), Secondary link       │   │
│  └──────────────────────────────────────────────────┘   │
│                                                          │
├──────────────────────────────────────────────────────────┤
│  FOOTER (full-bleed bg-neutral-950, py-16)              │
│  ┌──────────────────────────────────────────────────┐   │
│  │ Link columns + copyright + social                │   │
│  └──────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────┘
```

**Landing mode forbidden patterns checklist:**
- [ ] Sidebar navigation? **REJECT** — use header nav.
- [ ] Data table or functional form as primary content? **Maybe wrong mode** — is this actually APP?
- [ ] Authenticated user elements (avatar, "My projects", workspace)? **REJECT** — landing is for visitors.
- [ ] Tabbar? **REJECT** — never on desktop, and never on marketing.
- [ ] No footer? **Missing required element** — landing pages must have footers.
- [ ] No hero section? **Missing required element** — landing starts with a hero.

### 4.3 DOCS Mode Composition Rules

**Mandatory elements:**
- Search bar: prominent, in the topbar or at the top of the sidebar. Full-text search with autocomplete is implied.
- Sidebar navigation: sticky, multi-level tree of documentation sections. Collapsible categories. Current page highlighted.
- Content area: prose-optimized, max-width ~720 px for readability. Headings follow logical outline (h1 → h2 → h3, no skipped levels).
- Code blocks: syntax-highlighted, dark background, copy button at top-right.
- "On this page" (TOC): optional right sidebar showing h2/h3 anchors for the current page. Sticky.

**Optional but recommended:**
- Breadcrumbs: at the top of the content area.
- Edit on GitHub link: bottom of each page.
- Previous/Next page navigation: at the bottom of the content.
- Dark mode toggle: prominent, in the topbar.

**Layout template for DOCS mode:**

```
┌──────────────────────────────────────────────────────────┐
│ TOPBAR (sticky top-0): Logo | Search bar | Theme toggle  │
├────────────┬─────────────────────────────┬───────────────┤
│ SIDEBAR    │ MAIN CONTENT                │ TOC (right)   │
│ (sticky,   │ (max-w-[720px], prose)      │ (sticky,      │
│  scroll)   │                             │  optional)    │
│            │ Breadcrumbs                  │               │
│ Guides     │                              │ On this page  │
│  ├ Getting │ # Heading 1                  │ • Subheading  │
│  │ Started │                              │ • Subheading  │
│  ├ Tutorial│ Lorem ipsum dolor sit amet,  │               │
│  └ FAQ     │ consectetur adipiscing elit. │               │
│ API Ref    │                              │               │
│  ├ Auth    │ ## Heading 2                 │               │
│  ├ Endpts  │                              │               │
│  └ Errors  │ Sed do eiusmod tempor...     │               │
│ SDKs       │                              │               │
│  ├ JS      │ ```js                        │               │
│  └ Python  │ const data = await...        │               │
│            │ ```   [Copy]                 │               │
│            │                              │               │
│            │ ← Previous  |  Next →        │               │
└────────────┴─────────────────────────────┴───────────────┘
```

**Docs mode forbidden patterns checklist:**
- [ ] No search bar? **Missing required element.**
- [ ] No sidebar navigation? **Missing required element** — docs need section nav.
- [ ] Hero section or CTA-focused content? **REJECT** — docs are functional, not persuasive.
- [ ] Code blocks without syntax highlighting or copy button? **Incomplete.**
- [ ] Centered, wide content (full 1280 px for reading)? **Wrong** — docs use max-w-prose (~65ch).
- [ ] Footer with marketing links? **Fine for docs** — footers are acceptable on documentation sites. This is the one exception to the "no footer on app" rule because docs are web-first, not app-first.

### 4.4 SOCIAL Mode Composition Rules

**Mandatory elements:**
- Feed/timeline: central content column. Posts, updates, or messages arranged chronologically.
- Compose/create action: prominent button or input for creating new content (post, message, comment).
- Interaction indicators: like/favorite counts, comment counts, share counts, timestamps.
- User identity: avatar + name on every content item. Real-time indicators (online dot) if applicable.

**Allowed layouts:**
- **Three-column social:** Left sidebar (nav, filters, communities), center (feed), right sidebar (trending, suggestions, activity).
- **Two-column messaging:** Left (conversation list), right (active conversation).
- **Single-column feed:** Simpler products — feed only, with a topbar for navigation.

**Layout template for SOCIAL mode:**

```
┌──────────────────────────────────────────────────────────┐
│ TOPBAR: Logo | Search | Compose button | Avatar          │
├──────────┬──────────────────────┬────────────────────────┤
│ SIDEBAR  │ FEED                 │ RIGHT PANEL            │
│ (nav)    │                      │ (trending / activity)  │
│          │ ┌──────────────────┐ │                        │
│ Home     │ │ Compose box      │ │ Trending topics         │
│ Explore  │ │ [What's new?]    │ │ • Topic 1 (2.3k posts) │
│ Notifs   │ └──────────────────┘ │ • Topic 2 (890 posts)  │
│ Messages │                      │                        │
│ Bookmarks│ ┌─ Post ───────────┐ │ Who to follow           │
│ Profile  │ │ Avatar • Name    │ │ • Person 1 [Follow]    │
│          │ │ @handle • 2h ago │ │ • Person 2 [Follow]    │
│          │ │                  │ │                        │
│          │ │ Post content...  │ │                        │
│          │ │                  │ │                        │
│          │ │ ♡ 42  💬 12  ↻ 5│ │                        │
│          │ └──────────────────┘ │                        │
│          │                      │                        │
│          │ ┌─ Post ───────────┐ │                        │
│          │ │ ...              │ │                        │
│          │ └──────────────────┘ │                        │
└──────────┴──────────────────────┴────────────────────────┘
```

**Social mode forbidden patterns checklist:**
- [ ] No feed or messaging structure? **Wrong mode** — check if this is actually APP (content list) or LANDING.
- [ ] No compose/create action? **Missing key interaction** — social products need a way to post/send.
- [ ] No interaction counts or timestamps? **Incomplete** — social content must have engagement metadata.
- [ ] Testimonials or pricing? **REJECT** — social products are for interaction, not marketing.
- [ ] Data table or KPI cards as primary content? **Wrong mode** — this is APP, not SOCIAL.

## 5. Mode Switching & Conflict Resolution

### 5.1 Mode Contradiction Detection

Picasso must detect when the detected mode contradicts the composition plan. This is the single most important quality gate for mode correctness.

**How contradictions occur:**
1. The prompt explicitly says "app" or "dashboard", but the generated layout includes a centered hero section with a marketing CTA → **Contradiction detected.** The layout plan must be rejected and rewritten in APP mode.
2. The prompt says "landing page", but the layout includes a persistent sidebar navigation → **Contradiction detected.** Sidebar = APP, not LANDING.
3. The prompt says "documentation", but there is no search bar and no sidebar section navigation → **Contradiction detected.** Missing DOCS-mode mandatory elements.
4. The prompt is ambiguous ("design a screen"), but the layout defaults to a landing page with hero section → **Contradiction if no landing triggers exist.** Default to APP mode for ambiguous prompts. APP is the default, not LANDING.

### 5.2 Contradiction Resolution Protocol

When a contradiction is detected:

```
1. PAUSE generation.
2. IDENTIFY the contradiction: "Layout uses [LANDING pattern] but is labeled [APP mode]."
3. RESOLVE: Discard the current layout plan. Rewrite using the correct mode's composition rules.
4. VERIFY: Check against the mode's mandatory elements and forbidden patterns checklists.
5. PROCEED with the corrected plan.
```

**Never** proceed with a contradictory layout because "the user might not notice." Picasso must enforce mode correctness before aesthetic evaluation.

### 5.3 Prompt Heuristics When Both Modes Are Mentioned

Some prompts describe products that span multiple modes. Picasso must handle these by generating separate outputs, not by merging modes:

| Prompt Pattern                                        | Handling                                                                    |
|-------------------------------------------------------|-----------------------------------------------------------------------------|
| "Design the landing page and the app dashboard"       | Generate TWO screens: one LANDING, one APP. Never merge.                    |
| "Design a website for our SaaS product"              | "Website" = LANDING. Ask: "Do you also need the authenticated app screens?" |
| "Design the docs site with a landing page for the API"| Generate TWO screens: one LANDING (API overview/product), one DOCS (reference). |
| "Build a community platform" (ambiguous)              | Ask: "Is this the marketing page for the community, or the community feed/app?" |

### 5.4 Hybrid Products

Some products have marketing surfaces AND app surfaces. Picasso must treat these as separate modes, never blended:

- **SaaS product:** LANDING mode for the marketing site (homepage, pricing, about). APP mode for the authenticated product (dashboard, settings, workflows). These are different domains, often on different subdomains (app.product.com vs product.com).
- **Documentation site:** DOCS mode for the reference content. LANDING mode for the docs homepage (if it has a hero/CTAs/social proof). The docs homepage and the docs content pages are different modes.
- **Social product:** SOCIAL mode for the feed/interaction surface. LANDING mode for the marketing homepage. These are separate.
- **Developer tool:** APP mode for the authenticated workspace. DOCS mode for the API reference. LANDING mode for the marketing homepage. Three modes, three separate designs.

**Rule: If a product has both marketing and functional surfaces, Picasso must generate them as separate screens in separate modes. Never blend a sidebar with a hero section. Never put a pricing table on a dashboard.**

## 6. Anti-Slop Enforcement by Mode

Each mode has specific slop patterns that must be caught and rejected. These are the most common mode-specific failures:

### 6.1 APP Mode Anti-Slop

| Violation                                    | Severity    | Action                                     |
|----------------------------------------------|-------------|--------------------------------------------|
| Marketing hero on app screen                 | CRITICAL    | Immediate rejection. Rewrite as functional.|
| Footer on desktop app screen                 | CRITICAL    | Remove footer.                             |
| Tabbar on desktop app screen                 | CRITICAL    | Replace with sidebar or topbar.            |
| "Sign in" / "Get started" in topbar          | CRITICAL    | Replace with user avatar + workspace name. |
| Sparse content (one welcome message, no data)| HIGH        | Populate with meaningful product data.     |
| Testimonial or pricing section               | HIGH        | Remove. Not appropriate for app screens.   |
| Centered layout without functional split     | MEDIUM      | Add sidebar or functional grid.            |
| More than 3 cards                            | MEDIUM      | Replace with table, list, or rows.         |
| Carousel                                    | MEDIUM      | Remove. Use static grid or list.           |

### 6.2 LANDING Mode Anti-Slop

| Violation                                    | Severity    | Action                                     |
|----------------------------------------------|-------------|--------------------------------------------|
| No hero section                              | CRITICAL    | Add hero section at top.                   |
| No footer                                    | CRITICAL    | Add footer with links, legal, copyright.   |
| Sidebar navigation instead of header nav     | HIGH        | Replace sidebar with top header nav.       |
| Authenticated user elements (avatar, workspace)| HIGH     | Remove. Landing is for unauthenticated visitors. |
| Data table or CRUD form as primary content   | MEDIUM      | Replace with persuasive/marketing content. |
| "Get started" + "Learn more" CTA pair        | HIGH        | Write specific CTA copy.                   |
| Blue-to-purple gradient hero                 | CRITICAL    | Replace with single-color or no-gradient.  |
| Circular avatar testimonial carousel         | CRITICAL    | Replace with row/grid testimonials.        |
| Floating decorative blobs                    | HIGH        | Remove. Use real product screenshots.      |

### 6.3 DOCS Mode Anti-Slop

| Violation                                    | Severity    | Action                                     |
|----------------------------------------------|-------------|--------------------------------------------|
| No search bar                                | CRITICAL    | Add prominent search.                      |
| No sidebar navigation                        | CRITICAL    | Add section-nav sidebar.                   |
| Hero section with CTA                        | CRITICAL    | Remove. Docs are informational.            |
| Content too wide (>720 px prose)             | MEDIUM      | Cap content at max-w-prose.                |
| Code blocks without copy button              | MEDIUM      | Add copy button to all code blocks.        |
| No heading hierarchy (h1→h2→h3)              | MEDIUM      | Enforce logical heading outline.           |
| Missing "on this page" TOC (long pages)      | LOW         | Add TOC for pages with >3 h2 sections.     |

### 6.4 SOCIAL Mode Anti-Slop

| Violation                                    | Severity    | Action                                     |
|----------------------------------------------|-------------|--------------------------------------------|
| No feed or messaging structure               | CRITICAL    | Add feed, timeline, or conversation layout.|
| No compose/create action                     | CRITICAL    | Add prominent post/message creation.       |
| No interaction metadata (likes, comments)    | HIGH        | Add counts, timestamps, reactions.         |
| Data table as primary content                | HIGH        | Replace with feed-style content display.   |
| Marketing hero                                | HIGH        | Remove. Feed is the primary content.       |
| No user identity on content items            | MEDIUM      | Add avatar + name to every post/item.      |

## 7. Mode Switching During a Session

### 7.1 If the User Changes the Context

If a user asks for an app screen and then asks for a landing page in the same session, Picasso must explicitly acknowledge the mode switch and adjust all composition rules:

```
User: "Design a dashboard for my CRM."
Picasso: [Generates APP mode dashboard.]
User: "Now design the landing page for the same product."
Picasso: [Acknowledges mode switch. Generates LANDING mode page with same brand tokens.]
```

### 7.2 Persisting Brand Tokens Across Modes

When switching modes for the same product, Picasso must carry forward:
- Typography (display font, body font, weights, scale)
- Color palette (accent, neutrals, semantic colors)
- Corner radius philosophy
- Icon set
- Brand name and specific product context

The mode changes the LAYOUT and COMPOSITION, not the visual identity. The landing page and the app dashboard for the same product should look like they belong to the same brand.

### 7.3 Explicit Mode Declaration

When outputting a screen spec, Picasso should declare the mode explicitly:

```
MODE: app
PRODUCT: Projectly CRM
SCREEN: Team Dashboard
STYLE SEED: minimal/serious
...
```

This declaration serves as a self-check: if the declared mode is `APP` but the spec includes a hero section, the contradiction is immediately visible in review.

## 8. Quick Reference: Mode Detection Cheat Sheet

| Prompt Contains...                                    | Mode    | Key Layout Elements                                        | Forbidden                                |
|-------------------------------------------------------|---------|------------------------------------------------------------|------------------------------------------|
| dashboard, app, tool, admin, settings, workspace, CRM | APP     | Sidebar/topbar, no hero, no footer, functional content     | Hero, footer, tabbar, marketing copy     |
| landing page, hero, pricing, testimonials, conversion  | LANDING | Hero, feature grid, social proof, pricing, CTA flow, footer| Sidebar, data tables, authenticated UI   |
| docs, API, reference, documentation, knowledge base   | DOCS    | Search bar, sticky sidebar nav, prose content, code blocks | Hero, CTAs, marketing copy               |
| feed, social, messaging, chat, community, posts       | SOCIAL  | Feed/timeline, compose action, interaction counts          | Data tables, marketing hero, pricing     |

**When in doubt:**
1. If no marketing triggers → default to APP.
2. If the prompt mentions BOTH marketing AND app → generate two separate screens.
3. If genuinely ambiguous → ask the user.
